# CLAUDE.md — Relative-Value Forward-P/E Dashboard (operating manual)

> **How to use this file.** Drop it in the repo root as `CLAUDE.md` (Claude Code reads it automatically) and keep the source files described in §2 alongside it. This is a complete operating manual: it assumes **no prior conversation context**. Read §1 (what this is), §3 (build), §4 (the gate), and §7 (refresh) before changing anything.

> ⚠️ **Licensing first (see §11).** The dashboard **embeds licensed Bloomberg 1-year-forward (FY+1) P/E and S&P-Global-derived adjusted prices** directly in the HTML. Anyone who can open the file can read the data. **Do not publish to a public site.** Private repo + access control only.

---

## 1. What this is

A **single, self-contained interactive HTML dashboard** for a long/short **diversified-financials** equity investor. It does relative **1-year-forward (FY+1) P/E** valuation across **91 names in 7 sub-sectors**, plus validated **mean-reversion pair backtests**, **per-pair quarterly consistency** analysis, single-name P/E history, a sub-sector small-multiples grid, a **click-to-measure share-price-return tool** on the pair chart, and a **Software reference tab for JKHY**.

**Technical shape**
- **No runtime dependencies, no framework, no build step needed to *view*.** Plain HTML + one inline `<script>` of vanilla JS + inline SVG + one `<canvas>`. Opens by double-click. Current size ≈ **2.1 MB**.
- **All data is embedded** as JavaScript constants near the top of the script (see §5).
- **Eleven tabs** (§6): Pairs · Name P/E · **Software** · Flags · Summary · Screen · Matrix · Grid · Coverage · Consistency · Backtest.
- CSS is one `<style>` block themed entirely with custom properties (`--ink`, `--ink2`, `--muted`, `--faint`, `--line`, `--line2`, `--bg`, `--panel`, `--panel2`, `--accent`, `--series` `#15697A`, `--avg` `#E2733A`, `--cheap` `#2E7D52`, `--rich` `#C0392B`, `--mono`, `--sans`).

**The product is the file `Relative_PE_Dashboard.html`.** Everything else exists to regenerate it reproducibly.

## 3. Build pipeline (token replacement)

The build replaces the 6 tokens in `template.html` with their JSON payloads. **Order matters:** `__DATA__` is a substring of `__QDATA__` and `__BTDATA__`, so those must be replaced first. `__DPX__`, `__SWDATA__` and `__XPE__` are independent (none contains, or is contained by, `__DATA__`). Replace each exactly once and assert none remain.

The relevant declarations in `template.html`:
```js
const DATA = __DATA__;
const BT   = __BTDATA__;
const QD   = __QDATA__;
const DPXMETA = __DPX__;
const DPX  = DPXMETA.px;   // daily price map keyed by ticker
const SW   = __SWDATA__;   // software reference panel {asof, names, pe}
const XS   = __XPE__;      // reference series {series:{key:{base,label,...,dates,pe}}}: calendarized P/E etc.
```

`build.py`:
```python
import pathlib
tpl = pathlib.Path("template.html").read_text(encoding="utf-8")
out = tpl
ORDER = [("__QDATA__","q_pairs.json"), ("__BTDATA__","btdata.json"),
         ("__DATA__","data.json"), ("__DPX__","daily_px.json"), ("__SWDATA__","sw_data.json"),
         ("__XPE__","xs_data.json")]
for tok, f in ORDER:
    assert tpl.count(tok) == 1, f"{tok} count != 1"
    out = out.replace(tok, pathlib.Path(f).read_text(encoding="utf-8").strip(), 1)
assert not any(t in out for t,_ in ORDER), "token left"
pathlib.Path("Relative_PE_Dashboard.html").write_text(out, encoding="utf-8")
print(f"built Relative_PE_Dashboard.html ({len(out)/1e6:.2f} MB)")
```

## 4. Validation gate — **non-negotiable, run after every rebuild**

Two checks. Both must pass before the file is considered good or deployed. (The Software tab is isolated — it does not affect the gate — but always run the gate anyway.)

**(a) JS syntax.** Extract the largest `<script>` from the built HTML and `node --check` it:
```bash
python3 -c "import re;h=open('Relative_PE_Dashboard.html',encoding='utf-8').read();open('/tmp/app.js','w',encoding='utf-8').write(max(re.findall(r'<script>([\s\S]*?)</script>',h),key=len))"
node --check /tmp/app.js   # must exit 0
```

**(b) Backtest gate.** `node bt_verify.js` must print **`✅ ALL CHECKS PASSED (39 passed)`** (0 failed).

How `bt_verify.js` works (so you don't break it): it reads the built HTML, pulls the largest `<script>`, extracts the **portable backtest core** between the marker `function bmean(` and the comment `END PORTABLE CORE`, extracts the `CLUSTERS` array by bracket-balancing, parses `data.json` + `btdata.json`, runs `btPrep()`/`meanIC()`, and compares ~39 outputs (pair IC at 1/3/6/12m, single-name IC, the 6-month buy-the-discount conditional mean/N/hit, portfolio Sharpe/mean/vol/N, pair count, trend-filter splits) against `bt_results.json` with tolerances. It is a **self-consistency check**: the HTML engine must reproduce the Python reference. So if you change the backtest data, **regenerate `bt_results.json` with `python bt_export.py` before running the gate** — otherwise engine and reference diverge and it "fails" spuriously.

If you edit the core's math, keep the `function bmean(` start marker and the `END PORTABLE CORE` end comment intact, and keep the core **DOM-free** (the verifier rejects it if it references `document.`/`getElementById`).

## 5. Data model (the embedded constants and their files)

**`data.json` → `const DATA`** — the valuation panel.
- `asof`: ISO date in the header.
- `dates`: array of **weekday-only** ISO dates (a rolling ~6-year window; the current span and row count are in §12). **No weekend rows** (see §9).
- `pe`: `{ "<TICKER>": [number|null, …] }` — daily **1-year-forward (FY+1) P/E**, aligned to `dates`. Tickers are Bloomberg-style: `"CME US"`, `"LSEG LN"`, `"DB1 GY"`, `"EQT SS"`, …
- `sectors`: `{ "<Sub-sector>": ["<TICKER>", …] }` (the 7 sub-sectors, §8).
- `sector_of`: reverse map. `excluded`: coverage tickers with no data in the workbook (currently none).

**`btdata.json` → `const BT`** — **monthly** price panel for the Backtest tab.
- `XMONTHS`: ~49 month-end ISO dates (currently `2022-06` … `2026-06`). `PX`: `{ "<name>": [monthly adjusted close|null] }`. Byte-identical content to `prices_all.json`. **Not** changed by the daily refresh. **The backtest return window starts 2022-06 because this panel does** (§7d).

**`q_pairs.json` → `const QD`** — precomputed per-pair quarterly records (101). Each: `a`,`b`,`sec`,`nq`; headline `hit`,`avgq`,`cum`,`ic`,`devnow`; `q`: `[{p,dm,dev,long,ret,win}]` per quarter; `ser`: the monthly premium/discount series `{t:"YYYY-MM", d:%-vs-expanding-avg}`.

**`daily_px.json` → `const DPXMETA`, then `const DPX = DPXMETA.px`** — **daily** price panel for the click-to-measure tool.
- `{ asof, note, px:{ "<TICKER>": [number|null, …] } }`, `px` aligned to `DATA.dates`.
- **S&P-Global daily ADJUSTED close (total return), local currency, single back-adjustment basis** (§7c), holiday-forward-filled, `null` before each listing/IPO date.

**`sw_data.json` → `const SW`** — the **Software reference panel** (for the JKHY tab only).
- `{ asof, names:["MSFT US",…], pe:{ "<TICKER>": [number|null, …] } }`, `pe` aligned to `DATA.dates`.
- Daily 1-year-forward (FY+1) P/E for 8 software names (MSFT, ORCL, CRM, NOW, WDAY, ADBE, INTU, ADSK). **JKHY is deliberately NOT here** — the tab draws JKHY from `DATA.pe['JKHY US']` so it stays consistent with the rest of the dashboard. **These names are reference-only and are NOT in `DATA` / the 91-name universe**, so they never appear in Pairs/Screen/Matrix/Grid/Consistency/Backtest.

**`xs_data.json` → `const XS`** — **reference series**: alternative P/E bases for single names, shown in Name P/E and offered as a Pairs basis option (added 2026-10-29; workbook-fed since 2026-10-30).
- `{ series:{ "<KEY>":{ base, label, short, kind, desc, note, pairnote, src, added, dates:[ISO…], pe:[number…] } } }`, built by `mkxs.py`.
- **Source: the workbook's CALENDARIZED block** (added by the investor 2026-10-30). Columns CQ–DG of sheet `HC` carry Bloomberg `pe_ratio(fpt=ba, fpo=2, fye=c1231, ae=e, …)`, i.e. FY+1 P/E **calendarized to a December year-end**, for the 17 non-December year-end names: AFRM, AJB, BEN, BILL, EXPN, FDS, FICO, HLI, HLNE, ICG, IGG, JKHY, RJF, STEP, V, WISE, WLTH (HLI, column DG, was added in the third 30 Oct workbook). The block has **its own date column (CP)**, calendar-daily from 2020-01-01, different from column A, and it **repeats tickers** from the FY+1 block. `mkdata.py` therefore reads the FY+1 panel only from the columns before CP, and writes the calendarized block, keyed by CP's dates, to `cal_pe.json` (weekdays only, capped at `ASOF`, trimmed to the panel start, 2 dp, missing values left missing). `mkxs.py` turns each into series `<TICKER> CAL` (label `<TICKER> · calendarized`, `src: 'workbook'`). It asserts `cal_pe.json`'s `asof` equals `data.json`'s, so a stale file cannot slip through.
- **Stored by its own dates, not aligned to `DATA.dates`.** `template.html` aligns each series to `D` at load (`XPE[key]`). A panel date a series lacks stays `null`; BILL lacks 283 dates in its span and IGG 363.
- **What the basis is:** most of the year it covers the same calendar year as a December-year-end peer's FY+1 (RJF on 29 Oct: implied EPS 14.7 against FY2027 14.3 and FY2028 16.1 on Capital IQ, i.e. CY2027; HLI on 29 Oct: implied EPS 8.47, between the Capital IQ consensus for the years to March 2027, 7.28, and March 2028, 8.70). It still steps forward once a year, and when differs by name (measured from unexplained one-day moves vs price, 2021–26): **late January / early February**, close to the December peers' February roll, for V, RJF, BEN, FICO, JKHY, HLI, HLNE, STEP, BILL and AFRM; **late March** for FDS; **May** for EXPN, ICG and AJB. **Noisy series:** IGG (+26% on 2025-12-16, −57% on 2026-07-30), WISE (many 10–25% jumps), WLTH (from Jan 2026; up to +79%/−85% in Feb–Mar 2026, −40% on 2026-10-09), AFRM (noisy before 2025, up to 165x) and BILL (near-zero earnings put it above 200x on 108 dates in 2021–23, up to 16,502x). **RJF dips about 14% from 2026-10-01 to 10-12 on a flat share price and snaps back on 10-13**, a likely vendor glitch. All are sourced and kept (§7); each series' note in the page says which applies.
- **The BQL date range is hard-coded** (`dates=range(2020-01-01,2026-10-29,…)`), unlike the FY+1 block's `range(-6y,0d)`. If the investor does not extend it, the series stops and the page reads "P/E at <date>" (stale handling below).
- **Pasted series** (`PASTED` in `mkxs.py`, `src: 'paste'`) are still supported but there are none now. **The RJF calendarized 2-yr-forward paste of 2026-10-29 was retired on 2026-10-30**: it was a different measure (about two years out; 9.4x against 10.5x calendarized on 28 Oct) and stale, and the workbook series supersedes it. It is in git history (`xs_rjf_cy2.txt`, commit before #122).
- **Pairs basis option:** when a Pairs leg is a ticker that has a reference series, a **P/E basis** switch (`FY+1 | Calendarized`) appears on that leg's header line. `ST.aBasis`/`ST.bBasis` hold `''` (FY+1) or the series key; `legKey()` maps the leg to the series key, while the leg itself stays the ticker, so an aggregate on the other leg still leaves the name out and click-to-measure still reads its prices. The basis resets to FY+1 whenever another tab loads a pair (`initPairControls`), moves with the name on a swap, and clears if the leg changes. With it on, the cards read "At <date>" once the series ends before the panel. Above 900px the switch is absolutely positioned, so it never moves the layout: the V/MA and LPLA/RJF email charts (rendered at 960px) produce the identical canvas bitmap at the identical position. Below 900px it joins the header line and wraps; below 560px the "P/E basis" label hides.
- **Reference only, like `SW`:** it never enters `PE`, so no sub-sector aggregate, screen, Grid, Consistency record or backtest can see it; Pairs reaches it only through the basis switch.

**Tab → source:** Pairs/Name P/E/Flags/Summary/Screen/Matrix/Grid/Coverage derive from `DATA.pe` (Name P/E also lists the `XS` reference series, and Pairs offers them through the basis switch); the Pairs click-to-measure tool reads `DPX`; Consistency reads `QD`; Backtest reads `BT`; the **Software tab reads `SW` (+ `DATA.pe['JKHY US']`)**.

## 6. The tabs (brief)

- **Pairs** — relative forward P/E of leg A ÷ leg B over time, with premium/discount stats, a window gauge, and ±-range. Either leg can be a single ticker **or** a sub-sector aggregate (sentinels `~avg~<sector>` / `~med~<sector>`); a sector-aggregate leg **excludes the other leg's ticker** from its own average/median. **Custom basket** (added 2026-09-29): either leg's sub-sector menu also offers `Custom basket`, which opens a checkbox picker of all 91 names grouped by sub-sector (filter box, tick a whole sub-sector at once, Clear all). The leg then works exactly like a sub-sector aggregate: sentinels `~avg~Custom basket` / `~med~Custom basket` go through the same `legSeries()`, so the basket is equal-weighted, uses whichever members have a P/E on each date, and leaves out the other leg's ticker. One basket is shared by both legs and saved in the viewer's browser (`localStorage` key `pehistory.pairs.basket`, filtered to current tickers on load); it is never embedded in the page, so the email charts and other viewers are unaffected. Members are stored in sub-sector order, so a basket holding a whole sub-sector reproduces that sub-sector's built-in aggregate bit for bit. **Click-to-measure:** when leg A is a single ticker, click two dates on the chart to read **A's share-price total return** between them. Disabled with a hint when A is an aggregate. **P/E basis switch** (added 2026-10-29): a leg set to a ticker with an `XS` reference series (the 16 non-December year-end names) shows `P/E basis: FY+1 | Calendarized` on its header line (§5).
- **Name P/E** — single-name forward P/E vs its own history: ±1σ band, full-history mean, percentile, z-score, hover crosshair. A **High / Average / Low P/E table** sits at the top (added 2026-10-28; `npHiLo()` in `template.html`), with 1Y, 3Y and 5Y columns. It always runs trailing to the name's latest observation and ignores the chart's History window. Each high and low shows its date. A column longer than the name's history is headed "since <month>" (e.g. WLTH, CRCL). The name list also carries any **reference series** from `xs_data.json` right after its base ticker (currently the 17 `<TICKER> · calendarized` series, §5); each gets the same chart, cards and table, plus a note saying what it is and how it rolls.
- **Software** *(reference for JKHY)* — two pair-style selectors, **Focus** and **Compare to**, each drawn from a unified list: JKHY, **Software average**, **Software median**, and the 8 individual software names. The chart plots the two chosen series (focus teal, comparator orange) with the other software names as a faint backdrop; headline cards show each level, the focus-vs-comparator gap (red=richer/green=cheaper), and the focus's 5Y percentile; a reference table lists everyone with their own 5Y percentile. **Reference only** — `SW` is separate from the 91-name universe; nothing here feeds pairs/screens/the backtest. Default A=JKHY, B=Software median; state in `ST.swA`/`ST.swB`/`ST.swM`.
- **Flags / Summary / Screen / Matrix / Coverage** — cross-sectional cheap/rich views from `DATA.pe`.
- **Grid** — sub-sector small-multiple sparklines; each name vs its peer median/average (ex-self), or curated intra-sub-sector pairs; cross-sector "Compare to" hero card.
- **Consistency** — each curated pair scored as a quarterly side-switching mean-reversion trade; expandable annotated premium/discount chart.
- **Backtest** — IC by horizon, return-by-z bars, trend filter, net-of-cost P&L.
- **History windows** (Pairs, Name P/E, Software, Grid, Re-rate) — 1Y/3Y/5Y/Max presets plus **Custom** (added 2026-10-27), which shows From/To date inputs (`wireRange()`/`syncRange()` in `template.html`). Each tab's window state (`ST.m`, `ST.npM`, `ST.swM`, `ST.gridM`, `ST.rrM`) is a month count for a preset (0 = Max) or `{from,to}` ISO dates for Custom. `sliceMonths()` handles both, so any new windowed view should slice through it and label the window with `winText()`/`winShort()`, never with `m/12` arithmetic. Typed dates are put in order, clamped to the panel and snapped to trading days (at least two). Clicking Custom seeds the inputs with the dates the active preset covers, so nothing moves until a date is edited. When a custom window ends before the latest date, the "Current" cards and notes read "at window end". Windows are not saved between visits. The email charts always use presets (`mkcharts.mjs` sets month counts), so they are unaffected.

## 7. DATA REFRESH PROCEDURE

> **Hard rule: never fabricate, synthesise, interpolate, or placeholder a data point. Sourced primary data only. If a series is unavailable, drop the name — do not invent values.**

A full refresh updates the **P/E panel** (Bloomberg coverage workbook), the **daily price panel** (S&P Global), and — when a fresh software workbook is supplied — the **Software reference panel**.

### 7a. Forward P/E → `data.json`
1. The investor uploads a refreshed `Coverage_PE_multiples.xlsx` (sheet `HC`; ticker row at index 2; data from row index 5). It is **calendar-daily**, and **today's row, weekends, and US market holidays are forward-filled artifacts** — *not* clean closes.
2. In `mkdata.py` set `ASOF` to **the latest *settled* close** = the most recent completed US trading day that is **not today** (today's pull is intraday/forward-filled) and **not a market holiday**. The script caps at `ASOF` and applies a **weekday filter** (`dayofweek < 5`). Note holidays still appear as weekday rows in the workbook (forward-filled); the `ASOF` cap is what excludes them when they fall after the last real close. (Example seen in practice: a Friday Juneteenth + weekend + an intraday Monday pull ⇒ the latest settled close was the prior Thursday, so `ASOF` did **not** advance.)
3. Run `python mkdata.py` → `data.json` (2-dp rounding) and `cal_pe.json` (the calendarized block, §5); then `python mkxs.py` → `xs_data.json`. The universe is **SECTORS-driven**: any coverage ticker absent from the workbook (or all-null) is auto-`excluded`, and workbook columns outside the SECTORS lists are ignored — so vendor re-tickering can't silently change coverage.
4. Sanity-check span/row-count, **0 weekend rows**, and that historical overlap vs the prior `data.json` is stable (mean |Δ| ≈ 0.003x). New sourced P/E **revisions** on historical dates are normal (the vendor restates forward EPS — e.g. ENX FP, ICG LN, AMP US have all been restated across many dates) — take the new file as truth.

### 7b. Regenerate the dependent references
```bash
python mkxs.py        # -> xs_data.json    (reads cal_pe.json + data.json; after mkdata.py)
python q_pairs.py      # -> q_pairs.json    (reads data.json + prices_all.json)
python bt_export.py    # -> bt_results.json (reads data.json + prices_all.json)
python mksw.py         # -> sw_data.json    (reads bbg_software_mults.xlsx + data.json; §7f)
python build_dpx3.py   # -> daily_px.json   (after the S&P pulls in §7c)
```

### 7c. Daily prices → `daily_px.json` (S&P Global + the splice)
Source: the **S&P Global** connector (`get_prices_from_identifiers`, `periodicity="day"`, `adjusted=true`). Resolve each Bloomberg ticker with the **resolution map** below.

**Adjusted-price basis caveat (why the splice exists):** S&P adjusted closes are *back-adjusted to the fetch's end date*, so two fetches with different end dates sit on different bases and cannot be naively concatenated. `build_dpx3.py`:
1. The previously-stored full-history S&P pulls define the **reference basis** (the `base` dict).
2. To add new days **or** extend history, fetch the new segment **with overlap** into the existing series (recent: `2026-01-01 → <new asof>`; history extension: `<earlier start> → 2021-08-31`). Both windows are large enough that the connector stores them to files under `SP_PULLS_DIR` (default `tool_results/`); **process those files with Python, never paste them into context.**
3. Per name, compute a **constant scale factor** `F = median(base[d] / new[d])` over the overlap; **verify F is stable** (max deviation < 1% ⇒ no split artifact — flag anything larger). Multiply the new segment by `F` onto the reference basis.
4. Reassemble each name's date→price map, **realign to `data.json.dates`**, forward-fill exchange holidays, leave leading `null` before the listing date, round to 2 dp.
5. Verify seam continuity (joins are ordinary day-over-day moves), correct listing dates, and `len(px[t]) == len(dates)` for all 91.
6. **If nothing advances past the current asof** (e.g. a revisions-only refresh, or a holiday/intraday day excluded), no new pull is needed — just re-run `build_dpx3.py` to realign to the new date axis (the existing pulls already cover through the asof).

**Ticker → S&P identifier resolution map** (verified):
- **US (66):** plain ticker (`RJF`, `CME`, `SCHW`, …).
- **US needing exchange qualification (4):** `MA US→NYSE:MA`, `V US→NYSE:V` (plain "Visa" mis-resolves to TSX), `BAM US→NYSE:BAM`, `MC US→NYSE:MC` (Moelis; plain "MC" can hit LVMH).
- **Foreign (19):** `LSEG LN→LSE:LSEG`, `DB1 GY→XTRA:DB1`, `ENX FP→ENXTPA:ENX`, `EXPN LN→LSE:EXPN`, `WISE LN→LSE:WISE`, `ADYEN NA→ENXTAM:ADYEN`, `PGHN SW→SWX:PGHN`, `EQT SS→OM:EQT`, `CVC NA→ENXTAM:CVC`, `DWS GY→XTRA:DWS`, `AMUN FP→ENXTPA:AMUN`, `ICG LN→LSE:ICG` (**not** `ICP` — mis-resolves to a Kazakhstan listing), `FTK GY→XTRA:FTK`, `BGN IM→BIT:BGN`, `FBK IM→BIT:FBK`, `SAVE SS→OM:SAVE` (Nordnet), `IGG LN→LSE:IGG` (IG Group), `AJB LN→LSE:AJB` (AJ Bell), `AZA SS→OM:AZA` (Avanza).
- **Always verify** the returned `company_name`/exchange after a pull, especially foreign names and recent IPOs.

### 7d. Monthly prices → `btdata.json` / `prices_all.json` (only when extending the backtest)
Hard-coded, starts **2022-06**, which is why backtest *returns* start there even though the P/E baseline reaches 2020. The daily refresh does **not** touch it. To extend the backtest's return window earlier, pull **monthly** adjusted closes (same resolution map) back to the new start, rebuild `prices_all.json`/`btdata.json`, regenerate `bt_results.json`, re-run the gate.

### 7e. Rebuild + validate
`python build.py` → §4 gate → confirm `asof`, span, 0 weekend rows, the latest day present, `DPX` and `SW` span the full date range. Only then ship.

### 7f. Software reference → `sw_data.json`

## 9. Hard constraints / invariants (preserve in any refactor)

1. **Sourced data only** — never synthetic/interpolated/placeholder (§7 hard rule).
2. **Weekday-only + settled closes** — exclude weekends, **US market holidays**, and **today's intraday row**; `ASOF` = the latest settled close.
3. **Single adjustment basis** for the daily price panel — extend via the scale-factor splice (§7c), never naive concat.
4. **Sub-sector aggregates and the custom basket are equal-weighted** and **self-exclude** (the other leg's ticker is always left out).
5. **Color convention:** green = cheap / positive / won; red = rich / negative / lost. The generic `.pos`/`.neg` CSS classes are **intentionally inverted** (red for premium/rich) — reuse existing inline colors.
6. **Backtest math:** expanding-window z-score, **min 18-month** baseline; single-name signal = −z of own forward P/E; pair signal = −z of `ln(P/E_a / P/E_b)`; **population** standard deviation; monthly adjusted close, local currency, cross-currency legs FX-hedged; pair LS return = `r_A − r_B`.
7. **Software is reference-only and isolated** — `SW` must never be merged into `DATA`/the 91-name universe or the CLUSTERS; the Software tab must not feed pairs/screens/backtest. **The same holds for the `XS` reference series** (§5), including the calendarized block: they live in `XPE`, never in `PE`, and are shown only in Name P/E and through the Pairs basis switch.
8. **The gate (§4) must pass 39/39 after every rebuild.**

## 9b. The multiple is 1-year forward (FY+1), NOT NTM

**The uploaded workbooks supply a 1-year-forward multiple — the next full fiscal year (2027E for
December year-ends) — not a rolling next-twelve-months blend.** This was mislabelled as "NTM"
throughout the dashboard and this file until 2026-08-20; the labels are now corrected.

The analytical consequence is a **discrete annual roll**. The denominator does not creep forward
day by day; it steps once a year, on each company's own annual-results date, by roughly one year
of expected earnings growth. Verified against the price panel — the step shows up as a large
one-day fall in the multiple that the share price does not explain:

- **83–96% of the move lands on a single day** (CME: 2024-02-14, 2025-02-12, 2026-02-04).
- **Magnitude varies hugely by name, because it *is* the growth rate**: APO −16%, SPGI/MCO −11 to
  −12%, ICE −11%, CME −7%. Names with non-December fiscal years or mid-January reporting dates
  (V, BLK, SCHW) step in a different month, so it is *not* a universe-wide event.
- February is the modal month (median −8.3% unexplained drift across US names, against ±0.4% for
  every other month), because most December-FY US financials report then.

What it affects:
- **Single-name level statistics** (Name P/E percentile/z, Range band/CV/vol, Re-rate high/low)
  carry an annual sawtooth that inflates every dispersion measure.
- **Quarter-scoped windows are contaminated**: 77 of 91 names roll inside 1Q and none in 2Q/3Q.
  Splitting 1Q26 at each name's roll date cuts the median band from 38% to 18%, so ~half of a
  measured 1Q band is the roll. Cross-sectional *rankings* survive; levels and 1Q→2Q changes do not.
- **Calendar-year and rolling-year windows are self-consistent** — each contains exactly one roll
  per name.
- **Relative/pair work largely cancels** (both legs roll) but not fully: differing growth rates or
  fiscal year-ends leave a residual step of ~3–4% (CME/ICE +3.4%, APO/KKR +3.9%).

Both are documented in the Range and Name P/E footnotes. **Open decision:** whether to
roll-adjust the panel (rebase each pre-roll segment onto the post-roll basis, the same
scale-factor idea as the price splice in §7c) so level statistics become continuous. That would
change every published percentile and band, so it is a deliberate choice, not a silent fix.

## 10. Known gotchas

- **Ticker mis-resolution** on the S&P pull — use the §7c map; verify `company_name`/exchange; recent IPOs (CRCL, ETOR, FIGR, WLTH, MIAX, KLAR, CHYM, MQ, MRX, BAM, CVC, TPG, COIN, HOOD, TOST, SOFI, AFRM, BILL) only have data from listing.
- **US market holidays** look like ordinary weekday rows in the Bloomberg workbook (forward-filled) — they are **not** settled closes. Juneteenth, Labor Day, Thanksgiving, July 4th, etc. must be excluded from `ASOF` just like today's intraday row. **Columbus Day and Veterans Day are the exceptions:** US equity markets stay open (only bond markets close), so they are ordinary settled closes. Seen 2026-10-12: all 91 names moved, and S&P priced all 71 US names. **Diagnostic:** count how many names change vs the prior row. A settled US close moves ~all 91; a **US holiday moves only the 20 European names** (plus the odd US name on a vendor estimate revision); an early intraday pull moves a handful. (Seen 2026-09-07, Labor Day: 20 foreign + 4 US changed, so `ASOF` stayed Fri 4 Sep. **The same signature can appear on an ordinary trading day** when the pull's US pricing simply has not refreshed: on the 2026-09-09 workbook, Tue 8 Sep was a real US session yet 64 of the 71 US names were byte-identical to 4 Sep while all 20 Europeans had moved. Treat it identically — it is not a settled close. For a *relative-value* panel the mixed case is the worse one: advancing `ASOF` there would pair a current European leg against a stale US leg in every cross-border pair.)
- **Adjusted-price seams** — a >1% scale-factor deviation across the overlap means a split in that window; re-fetch that name's full history rather than splicing. **Check the shape first.** A split is a *step*: the base/pull ratio sits at one level before a date and another after it. A deviation confined to a *single date*, where the stored value equals the day before and F is exactly 1, is a stale forward-fill in the stored panel, not a split, and needs no re-fetch. The splice scripts print these as "single-date holiday ffill artifacts expected", which undersells them when the exchange actually traded that day. (2026-09-29: seven European names flagged >1%, every one on 2026-07-03 only; see the §12 known issue.)
- **`MQ US` sits on an F = 0.25 basis** — the reference basis holds Marqeta at a quarter of the S&P pull's price (e.g. 4.14 vs 16.58 on 2026-09-04), a 4:1 factor inherited from an early pull. F is stable (max dev 0.12%), so the splice is correct, but 2-dp rounding on a ~$4 price costs ~0.25% per observation, which is why MQ is the one name whose spliced day-over-day move can differ from the pull's by ~0.2pp. Harmless for `DPX`'s only consumer (click-to-measure reports *returns*, which are scale-invariant) — but if precision there ever matters, rebase MQ to F = 1.0 and re-round; that touches only MQ and leaves every reported return unchanged apart from less rounding noise.
- **A US market holiday inside `NEW_DATES`** breaks a naive splice guard. The splice template asserted all 71 US names were priced on every new date, which is right for an ordinary day but fires on a good pull when the US market was shut (S&P returns no close at all). `splice_910.py` discriminates: **no** US name priced = holiday, forward-fill (and assert some non-US name did trade, else the pull really is bad); **some** priced and others not = incomplete pull, halt. Carry that guard into future splice scripts.
- **Token substring order** — `__DATA__` ⊂ `__QDATA__`/`__BTDATA__`; replace the long ones first (§3).
- **`bt_verify` is self-consistent** — regenerate `bt_results.json` (`bt_export.py`) whenever backtest inputs change, or the gate "fails" only because the reference is stale. **Backtest headlines can move on an ordinary daily refresh** even though `btdata.json` is untouched: the backtest resamples P/E to month-end, so a sourced revision that lands on a completed month-end value can shift that month's signal — **but only month-ends inside the evaluated window matter.** Signals are scored against forward returns from the monthly price panel, which ends at its last `XMONTHS` entry (currently **2026-06**); a P/E month-end *after* that has no forward return and never enters an evaluated signal or baseline, so revisions there cannot move any backtest number. Since most daily revisions touch recent dates, most cannot move the backtest at all. Trace a move by diffing month-end P/E between the old and new `data.json`, then confirm by re-running `bt_export.py` in a scratch copy with only the suspect names' revisions applied. (2026-09-25: the 6m buy-the-discount mean moved +5.44% → +5.49%, n 864 → 863, Sharpe unchanged at 1.21. The scratch-copy test showed **FIS/CG 2024 revisions alone reproduce it exactly, and WISE/FOUR 2026 revisions have zero effect** — their Jul/Aug 2026 month-ends are past the June price panel. The next round confirmed it naturally: FOUR's August month-end reverted and `bt_results.json` came out byte-identical.) **The rolling window moves the backtest once a month, with no revision at all.** The workbook is a fixed ~6-year window, so on the first refresh after its start date crosses a month boundary, the oldest month drops out of the monthly resample entirely. Every expanding-window baseline then loses its first observation, every z-score shifts slightly, and the headlines move. Where a pair's z sat near zero at a decision month, its Consistency side can flip too. (2026-10-01: the start moved to 2020-10-01, so September 2020 dropped. Scratch-copy runs showed that drop alone takes the 6m mean from +5.49% to +5.35% (n 863 → 872). The AMUN restatement alone gives +5.47% (n 864), and the FDS 31 Mar tweak has no effect. All three together reproduce `bt_results.json` byte for byte.) Expect a similar small move on the first refresh of every month. It would stop while the baseline start is frozen (§12 open decision).
- **Compare `q_pairs.json` records by pair `(a, b)`, never by position.** `q_pairs.py` sorts records by hit rate, so when hit rates move, the order changes and a positional diff pairs up different records. On 2026-10-01 a positional diff reported 17 pairs gaining or losing quarters; keyed by pair, no pair's quarter count changed.
- **Big S&P pulls** land under `SP_PULLS_DIR` — parse with Python; don't read them into context.
- **SQN SW vendor-glitch hold** — the coverage workbook carries a spurious V-trough in Swissquote's forward P/E over 2026-05-29..2026-07-15 (−46% overnight, flat 7 weeks, +69% snap-back, share price stable). `mkdata.py` holds that window at the values sourced from the pre-glitch workbook (`HOLD` dict, investor decision 2026-09-03); a refresh therefore shows **0 historical diffs** for SQN SW even though the raw workbook still differs. Remove the block only once the vendor corrects the series.
- **Single-day vendor blow-ups — the `DROP` block.** Separate from the `SQN SW` HOLD above. A workbook can print a single observation that is simply wrong, with no earlier workbook holding a good value for that same date (because the date is brand new). HOLD cannot help there — there is nothing sourced to re-pin to — and carrying the prior day forward would be fabrication, so §7's hard rule ("if a series is unavailable, drop the name") makes **dropping the observation to `null`** the correct treatment. `mkdata.py` carries a `DROP = {ticker: [dates]}` block when one is needed. **It is currently empty, which is the normal state.** It was last used for `CRCL US` 2026-10-15/16 (1.79x against 51.31x the day before, on a +9.3% share price) and `SPGI US` 2026-10-16 (12.07x against 21.06x, on a +1.1% share price). The vendor fixed all three in the 2026-10-20 workbook, three trading days later for SPGI and four for CRCL, and the entries were removed. **Seen 2026-09-11: `TOST US` printed 0.84x against 24.16x the day before (−96.5% overnight) while Toast's share price moved +0.6% (31.94 → 32.12)** — an FY+1 EPS wrong by ~29x. **The vendor corrected it three days later** (the 2026-09-15 workbook restated 11 Sep to 24.29x, between 24.16x on 10 Sep and 25.18x on 14 Sep), and the block was removed on 2026-09-15 — so a `DROP` entry is a temporary hold, and **each refresh should re-check whether its dates have been fixed and remove the entry once they have.** **The discriminator is always price:** a real one-day multiple move is reproduced by the share price almost exactly (that same day `FTK GY` −7.9% P/E vs −7.88% price, `FISV US` +5.4% vs +5.42%), and the annual FY+1 roll (§9b) steps by a growth rate of order 10%, never 96%. A trailing `null` is safe — `lastVal()` scans back to the last non-null, the Grid pre-filters, and `backtest.py`'s month-end resample skips nulls — so the name falls back to its previous observation instead of showing a broken one.
- **Always outlier-scan the new day before publishing**, not just the historical diff: flag any name moving more than ±8% day-over-day or landing below 3x / above 200x, then cross-check each flag against the S&P price move. The historical-revision diff would never have caught the `TOST US` case, because the bad value was on the *new* date. **A large gap on a results day can be a genuine estimate reset, not a vendor error:** `LAZ US` 2026-10-22 printed +8.7% on a −0.2% share price (implied FY+1 EPS 3.58 → 3.29) on its Q3 results day, and the new level matched the Capital IQ FY2027 consensus (3.34 mean). Check the earnings date (`get_latest_earnings_from_identifiers`) and the consensus before treating a gap that size as a blow-up; the `DROP` cases were 40–96%, far outside any consensus range.
- **A fresh container has no `*.xlsx`** — the workbooks are gitignored (licensed vendor data, never committed), so `mksw.py` dies with `FileNotFoundError: bbg_software_mults.xlsx` whenever the session restarts and only the coverage workbook was re-uploaded. `realign_sw.py` is the fallback: `mksw.py`'s alignment step is a pure date-keyed lookup, so it can be reproduced exactly from the PREVIOUS `sw_data.json` plus the previous date axis (`/tmp/data_prev.json`) — re-key the stored values by their own dates, re-emit against the new axis. That re-indexes already-sourced values and invents nothing (§7 hard rule); the newly added trading day is after `SW_ASOF` anyway, so it comes out `null` exactly as `mksw.py` emits it. Run `mksw.py` whenever the workbook is present; this is only the fallback. **Also reinstall deps on a fresh container** (`pip install openpyxl pandas`, and `npm install playwright` in the scratchpad with `node_modules` symlinked into the repo for `mkcharts.mjs`).
- **When the S&P connector is unavailable, do NOT forward-fill the missing trading day.** The splice scripts' realign loop forward-fills, which is right for an exchange *holiday* (the market was shut, there is no close, carrying the prior one forward is the convention) but wrong for a real session whose closes simply could not be fetched — that presents a stale price as the day's close and silently corrupts every click-to-measure return ending on it. Use `realign_dpx_nofill.py`: re-key the stored prices by their own dates, re-emit against the new axis with **no fill past the last sourced date**, and leave `daily_px.json`'s `asof` at that last sourced date. `template.html` already handles the lag — `PXASOF = DPXMETA.asof` and `pxLagNote()` render a red banner saying prices run a day behind and the latest date was left blank rather than carried forward. **The P/E panel still advances**, because it comes from the uploaded workbook and needs no connector; only `DPX` lags, and `DPX` feeds nothing but click-to-measure. Backfill with the normal splice once the connector is authorized. (Seen 2026-09-20: connector disconnected and requiring re-auth, which a non-interactive session cannot perform.)
- **A vendor restatement can be TRANSIENT and revert exactly — price-independence cannot tell you which.** `KKR US` sat at 14.08x for 2026-09-09 in the 16 Sep workbook; the 17 Sep workbook cut the 09-09..09-16 block ≈ −2.7%, it held there through the 18 Sep workbook, and the **21 Sep workbook restored every date to the cent** (14.08x again, 0.00% across all six). At the time the cut showed the textbook restatement signature — contiguous block, tight uniform %, share price moving independently (−7.0% across the block) — and that signature was doing its job: it distinguishes a restatement from a price-driven artifact. What it *cannot* distinguish is a durable re-estimation from a transient one that will revert; only later workbooks settle that. **No special handling is needed** — taking each workbook as truth (§7a) puts the values back on its own, which is exactly what happened here, and the panel is correct at every vintage. But do not describe a fresh block as a settled restatement: call it what it is on the day, and expect some to reverse. Distinct from the `SQN SW` HOLD (a glitch that persisted) and the `TOST US` DROP (a single-day blow-up on a brand-new date). **Second example, faster:** the 24 Sep workbook re-based all of `FOUR US` 08-07..09-23 up a uniform ≈ +2.0%, and the 25 Sep workbook put **33 of 34 dates back on their 23 Sep values to the cent** — the re-base lived for exactly one workbook. It had been correctly reported as a fresh block (not a reversal of the 21 Sep cut) and not as settled; it simply did not survive. A name that has just flip-flopped deserves the same caution on its next revision. **Third example, a one-day step rather than a block:** `TOST US` jumped to a +16% FY+1 EPS level on 2026-10-08 with a flat share price, held it across three workbooks (10-11, 10-13, 10-14), and the 10-15 workbook put every date back on its pre-step value (10-08 exactly 22.70x again). **Fourth example:** the 2026-10-14 workbook finalised `CME US` 10-12 up 4.5% (an FY+1 EPS cut of about 3.8% on a −1.2% share price), the level held for three workbooks, and the 2026-10-20 workbook took 10-12..10-16 back down 4.65%, so the 10-12 move is again close to the price (−2.07% against −1.18%). **Fifth, the fastest:** the 2026-10-20 workbook recalculated 110 scattered `SCHW US` dates by ±0.1–0.9%, and the 2026-10-21 workbook put 109 of them back to the cent. **A second test for a fresh block: does the restated series explain the share price better or worse?** Sum the absolute unexplained day-over-day moves (log P/E move minus log price move) across the block and a few weeks either side, before and after. `MRX US` (2026-10-04) and `WLTH US` (2026-10-07) both got worse, each gaining steps at the block edges that the price does not explain. That is why both are flagged to the investor rather than reported as settled. It is evidence, not proof: an estimate can genuinely jump on a date with no price move.
- **Backfilling a blanked day is a different splice shape** — the axis does **not** move, so base is the *current* `daily_px.json` (not a previous-axis snapshot) and only the blank date is filled; `splice_920.py` is the worked example. **The substitute checks held up:** when the 2026-09-18 prices were backfilled, the real cross-check reproduced the connector-down verdicts to within 0.02pp on every flagged name, and the two "unchanged" names turned out to have had exactly flat prices. The substitutes below are sound, but confirm them against price once the connector returns.
- **The §10 price cross-check needs the connector.** With it down, an outlier flag on the new day cannot be confirmed against price. Substitutes that work from the panel alone: (a) **how routine is a move that size for that name** — `COIN US`/`HOOD US` exceed ±8% on ~10% of all days with a p99 |move| near 25%, so a +9..12% day is unremarkable for them; (b) **did the whole peer complex move together** — a coherent same-direction gradient across crypto-linked names (COIN +11.7%, HOOD +9.1%, CRCL +7.9%, FIGR +5.3% on 2026-09-18) is a sector move, the opposite of the `TOST US` signature of one isolated name moving while peers stayed flat; (c) for an *unchanged* name, how often it prints identical consecutive values historically (`BILL US`/`WLTH US` ≈ 4.8%, so two of 71 on a day is expected). State plainly that the price check could not be run.
- **Judge a name's "unexplained" daily move against its OWN baseline, not the universe's.** The price cross-check compares the day's P/E move with the day's price move; the gap is the day's change in the FY+1 EPS estimate. On a typical day the universe median gap is ~0.02pp, but names with an actively moving consensus run far wider every day: `WISE LN`'s own median daily gap since 2025 is 0.31pp with a p90 of 1.07pp, so its 0.77pp gap on 2026-09-23 (an EPS estimate uptick of ~0.8%) was exceeded on one day in six and is ordinary drift, not a fault. Compute the name's own distribution before treating a sub-1pp gap as suspect; a genuine blow-up (`TOST US`, §10 DROP) is orders of magnitude larger. Related diagnostic for the change-count check: one unmoved European name per day is normal **if the name rotates** (`BGN IM` 21 Sep, `DB1 GY` 22 Sep, `FBK IM` 23 Sep — FBK's price was also exactly flat); the **same** name unmoved day after day would point to a stale feed. **Count at full precision, not only at 2 dp.** The stale-feed signature is a *raw-identical* value. On a quiet day many names move by less than 0.005x and round to the same 2-dp value: on 2026-09-29 the 2-dp count showed 9 unmoved names (64/71 US, 18/20 European changed), but at full precision only `DB1 GY` was identical, and its price was exactly flat. That was a settled close.
- **Check panel alignment by DATE, not by length.** When `mksw.py` silently fails to run, `sw_data.json` keeps the *previous* axis — and because the axis is a fixed-width rolling window, it is still 1,565 long, so a length check passes while every value sits one trading day off. Same applies to `daily_px.json`. **Never pipe `realign_sw.py` (or `mksw.py`) through `head`.** On 2026-10-08, `realign_sw.py | head -2` died with a `BrokenPipeError` while printing, before it wrote `sw_data.json`. To prove a layout change left the charts alone, compare the rendered `#np-chart` `innerHTML` (and the `#chart` canvas state for pairs) between the old and new builds, not the PNG bytes.
- **The coverage workbook carries two blocks since 2026-10-30.** The CALENDARIZED block (CQ–DG) repeats tickers from the FY+1 block and has its own date column (CP). Any script that maps row-2 tickers to columns across the whole sheet breaks: on 2026-10-30 both `mkdata.py` and the change-count diagnostic failed with a pandas "truth value of a Series is ambiguous" error, because `data['RJF US']` returned two columns. Read the FY+1 block only up to the first column whose row-4 cell is `DATES` after column A, as `mkdata.py` now does (it also asserts the FY+1 block has no duplicate tickers).
